## Default pilot posture
- Use synthetic/anonymised data and mock external writes initially.
- Enable live integrations only when access and scope are explicitly agreed.
- Grant each tool the minimum required permissions.
- Deny actions outside the documented allowlist.
- Require human approval for external side effects unless an explicit narrow
  automated action has been agreed and recorded below.
- Fail safely when identity, authorisation or required evidence is unavailable.

## Identity and access
- Authenticate users through the application, not through statements in chat.
- Enforce record/client/tenant access on the backend for every tool call.
- Recheck permissions immediately before executing a side effect.
- Never allow the model to choose or override an authenticated identity.
- An unauthenticated pilot must use isolated synthetic data and restricted tools.

## Data protection and credentials
- Keep credentials in backend secret storage: .NET User Secrets locally and
  the hosting environment's secret facility in deployed environments.
- Never put secrets in React, VITE_ variables, prompts, fixtures or logs.
- Send only necessary data to the model; verify provider/data-handling constraints.
- Define permitted personal/confidential fields: [to clarify].
- Define log redaction, retention and deletion: [to clarify].
- Treat .gitignore and .clineignore as supporting exclusions, not access controls.

## Untrusted content and prompt injection
- Treat user text, retrieved documents and tool responses as untrusted data.
- Do not follow instructions within them that change policy, expose secrets,
  broaden access or request unrelated tool calls.
- Separate trusted instructions from retrieved content in the model context.
- Enforce tool permissions and data boundaries independently of model output.
- Validate URLs/destinations against an explicit allowlist when applicable.

## Output and evidence
- Validate structured outputs against a schema before using them.
- Validate business rules and identifiers on the backend.
- Use authoritative systems for balances, statuses and other business facts.
- Do not invent missing facts or report success before the operation succeeds.
- Ask for clarification or escalate when evidence is missing or contradictory.
- Render model output safely; avoid executing generated HTML/code.

## Human approval
- Present the exact proposed action, recipient/resource and relevant payload.
- Bind approval to that payload and authenticated approver.
- Record approver, time, action and outcome.
- Any material action change invalidates approval; request fresh approval.
- Define approval expiry and approver role: [to clarify].

## Operational limits and recovery
- Bound model/tool calls, retries, elapsed time and cost per request: [values].
- Apply timeouts and cancellation; retry only suitable transient failures.
- Use idempotency/state tracking for side effects and duplicate inputs.
- Persist workflow state where restart/recovery is required.
- Provide a stop/disable mechanism for automated side effects.
- Escalate visibly after retry limits; never loop indefinitely.

## Verification and observability
- Link each guardrail to cases in EVALS.md and relevant automated tests.
- Test bypass attempts at the API/tool boundary, not just through chat.
- Log correlation ID, authorised actor, tool/action, approval and outcome.
- Redact payloads and secrets; restrict access to audit records.
- Guardrail failures block pilot release until resolved or scope is reduced.
